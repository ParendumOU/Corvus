# Corvus for mobile

The app for Android and iOS (TestFlight) in `apps/mobile`: a private mobile browser, and the computer's Corvus in your pocket. It browses with the system's web view (Android's WebView, iOS's WKWebView), with tabs, history, bookmarks and the reading list synced end to end with the computers and ads and trackers blocked with the desktop's filter lists (Android). It has no AI provider of its own: it reads and writes the same end-to-end encrypted sync chain as the desktop app, and asks a paired computer for anything that needs Corvus itself (an AI answer, a page fetched for the reading list, a watched page checked).

## What it does

| Screen | What it shows or does | Sync collections |
|---|---|---|
| Corvus (home) | An address bar that starts browsing, the phone's own open tabs, the open tabs of every computer on the chain (with pins and tab groups), pages sent to this phone, pages it sent that wait to be opened, and a box that starts an Assist chat | `open_tabs`, `sent_tabs` |
| Browser | Web pages in tabs: an address bar that opens addresses or searches, back, forward, reload and stop, a progress bar, a tab switcher, and a menu with Corvus's actions on the page (Ask Corvus about it, send it to a computer, save it to the reading list, bookmark it, watch it) and the browser's own (share, find in page, open in another browser, desktop site, blocking on the site). See "The browser" below | `history`, `open_tabs`, `bookmarks`, `reading`, `watches`, `sent_tabs`, `asks`, `settings` (read) |
| Assist | One list of conversations, newest first and searchable: the chats of this phone (a computer answers them) and the Corvus Assist conversations had on the computers. A chat shows the answer as it is written (Markdown, [n] citations, sources as cards), suggested follow-ups that send, and a message box pinned at the bottom; the computer that answers is picked in the header | `asks`, `assist_history` |
| Library | Bookmarks by folder, the reading list (mark read/unread), history of every device by day | `bookmarks`, `reading`, `history` |
| Watched pages | What the computers last saw of each watched page, and a form to watch one more | `watches`, `watch_status` |
| Save or send a page | A page typed or shared from another app (Android share sheet): send it to a computer, save it to the reading list, bookmark it, watch it | `sent_tabs`, `reading`, `bookmarks`, `watches` |
| Open a link | "Open in…" from the browser's menu, or a web link from another app when pages open in another browser app (Android): open it in the picked browser with one tap, or send it or keep it as above | `sent_tabs`, `reading`, `bookmarks`, `watches` |
| Settings | Pairing, the chain's devices, unpairing, notifications, the browser (search engine, ad and tracker blocking, cookie banners, Global Privacy Control, clearing cookies and site data), default browser and where pages open (Android), version | |

**Notifications** (off until turned on in Settings, which asks the system's permission): pages a computer sends to this phone, and watched pages that changed. They are local notifications: about every 15 minutes, when the system allows it (`expo-background-task`: WorkManager on Android, BG tasks on iOS), the phone pulls the chain and notifies what is new. There is no push service.

**Language**: Spanish on a phone set to Spanish, English otherwise (`src/lib/i18n.ts`, `src/lib/i18n-es.ts`; a test checks every text has its Spanish one).

## How it fits with the desktop app

- **Pairing**: on the computer, Settings → Sync → "Pair a phone" shows a QR code with the sync server's address and the chain's recovery phrase. Anyone with it can read the synced data, so pair only your own phone. The phone scans it with a decoder that runs on the phone (see "The QR scanner has no Google code" below), or the details can be typed in. The phrase is kept in the OS's secure storage (Keystore / Keychain).
- **The sync server** only ever stores ciphertext. It has to be reachable from the phone. When the computer's sync server setting is `localhost` (e.g. the server in Docker on that computer), the QR code carries the computer's LAN address instead (same port; Tailscale or other addresses can be picked), the computer checks that the server answers there, and the pairing screen says the phone must be on the same Wi-Fi (allow the port in the firewall, pair again if the address changes). For any other address a phone likely cannot reach, such as a bare Docker name, the screen warns. A code from an older desktop that still carries `localhost` gets a specific error on the phone instead of the raw connection error.
- **Sending pages** both ways uses `sent_tabs`: the receiving device opens the page and deletes the record, which tells the sender it arrived. On the computer, "Send to your phone…" (tab and link menus) lists the paired phones.
- **Questions** (`asks`): the phone writes the question; the computer it went to answers it with its AI search (quick depth) and writes the answer into the same record as it streams in. Each computer decides whether it answers (Settings → Send to your phone → "Answer questions from Corvus on your phone", on by default). Corvus has to be open there.
- **Conversations** (`asks`): a follow-up carries `thread` (the id of the conversation's first question) and `context` (the last four answered questions and answers, oldest first, each answer cut to 1500 characters). The computer passes them to its AI search, which answers in that context (a `<conversation>` block in the prompt), searches a short follow-up ("and in winter?") together with the previous question, and caches it apart from the same words asked alone; it then marks the answer `withContext`. All these fields are optional: a Corvus that predates them answers the question alone, and the phone then notes under the answer that Corvus on that computer needs an update for follow-ups.
- **Where a question stands** comes from the device list: a computer running Corvus checks for questions every 5 seconds, so one not seen by the sync server for 90 seconds is "Corvus is not open there" (the question waits; it can go to another computer or be cancelled). One that is seen but has not taken the question after 45 seconds probably has "Answer questions from Corvus on your phone" off, and an answer that stops moving for 2 minutes can be asked again.
- **Corvus Assist conversations** (`assist_history`) are read in the same chat view, but they are tied to the page that was open on the computer, so the phone does not add to them. Writing below one starts a new chat of the phone that quotes it (`origin`) and carries its last turns as `context`, answered by the AI search of the computer picked.
- A sync server older than a collection the app uses refuses it; the app says the server needs updating instead of failing silently.

## The browser

Since 0.7.0 Corvus for mobile is a browser of its own. The browser is a full-screen screen over the tabs (`src/app/browser.tsx`), not a fifth tab: a page needs the whole height, and a browser toolbar under a navigation bar would leave two bars at the bottom. Home's address bar opens it with a new tab, Home's "N tabs open on this phone" row opens it on the last tab, every page the app opens (computers' tabs, Library, pages sent to the phone, an answer's sources) opens in it, and so do links from other apps while Corvus is the default browser. Only one browser screen is ever in the stack (`dangerouslySingular`), so a link that comes in while it is open goes to it.

- **Layout**: the address bar at the top (the shield with the count of what was blocked on the page, the site or the search, reload or stop), a 2 dp progress bar under it, and a toolbar at the bottom: back, forward, Corvus (back to Home), the tabs (with their count) and the page menu. Android's back goes back in the page, then closes a tab opened from another app and returns to that app (as browsers do), or a tab a page opened, else back to Home.
- **The address bar** (`src/lib/address.ts`, tested in `test/address.test.ts`) follows the desktop omnibox: `https://` addresses as typed, a domain with a known top-level domain (the list moved to `@corvus/shared`) gets `https://`, localhost and IP addresses `http://`, anything with a space, an e-mail address or another scheme (`javascript:`, `file:`, `intent:`…) is a search. Searches go to DuckDuckGo by default; Brave Search, Google and Startpage can be picked in Settings → Browser. Until the person picks one, the computers' synced home page setting (`appearance.homePage`, collection `settings`, which the phone now pulls read-only) chooses it when it is one of those. While typing, suggestions come from the phone's own tabs, bookmarks and history (`src/lib/suggest.ts`); nothing typed leaves the phone until it is searched or opened. On a results page the bar shows the search, elsewhere the site.
- **Tabs** (`src/lib/tabs.ts`, a pure reducer tested in `test/tabs.test.ts`): new, close, close all, switch in a grid (site icon, title, address), a tab a page opens (`target=_blank`, `window.open` on a tap) goes right after its opener, and closing it goes back there. The three tabs seen last keep a live page; the others load again when shown. Tabs are saved (AsyncStorage) and reopen after a restart. While paired, the phone publishes its web tabs as its own `open_tabs` record (keyed by its device id, as every device does; 3 seconds after they change, deleted when none is open), so the computers list them with their other devices' tabs.
- **History** (`src/lib/visits.ts`, `test/visits.test.ts`): a page counts as a visit when it finishes loading, once per page and tab (a reload, a redirect back or the page rewriting its own address within 30 seconds is the same visit). While paired it goes to the chain's `history` (one record per address, merged with what the computers recorded: count + 1, date, title), kept in the replica at once and pushed 4 seconds after the last visit; a computer that changed the same record meanwhile wins it and the phone's visit is counted on top. Unpaired, the phone keeps its last 500 visits for the address bar only.
- **Bookmarks and reading list**: the menu's star shows whether the page is bookmarked; it adds it to "Other bookmarks" or removes every bookmark of the page. Save to reading list and Watch this page work as on the Save or send screen; Send to a computer sends at once when there is one computer, else asks which.
- **Ask Corvus about this page** opens a new Assist chat about the page: a card with the page on top, suggested questions (summarize, key points, is the source reliable) and the computer that answers. On Android the page's title, description and main text (the `article` or `main` element) are read with the WebView's `evaluateJavascript`, which hands the value to the app only. The first question carries the page as the first turn of its `context` (question "The page I am reading: “title” (address)", answer the start of its text, cut to 1500 characters; the computer's AI search reads 600), so every Corvus that answers follow-ups answers it in that context, with no new field on the chain (`src/lib/page-ask.ts`, `test/page-ask.test.ts`). The chat keeps the page card (found again from that turn), and its follow-ups carry it like any context. On iOS the page's address and title go without its text.
- **Other actions**: share (the system's share sheet), find in page (Android: the WebView's own search, with the count and previous / next), "Open in…" (Android: the Open screen, which hands the page to the browser picked in Settings or sends it or keeps it), desktop site (Chrome on Linux's user agent for that tab, and the page loads again), and blocking on or off for the site.
- **Settings → Browser**: search engine, ad and tracker blocking on or off (with how many rules are loaded and when the lists were updated, "Update the lists now", and the sites it is off for), "Reject cookie banners" (Android, with the sites that keep their banner) and "Send Global Privacy Control" (both on by default, kept on the phone), and "Clear cookies and site data" (cookies, site storage and the cache of every site; tabs, history and bookmarks stay).
- **The web build** has no WebView: its browser screen shows a stand-in card that opens the page in a new browser tab, so the smoke check can still go through the address bar, the menu and the search offer.

### How pages are kept safe

The browser is `react-native-webview` 14 with the app's hooks (`patches/react-native-webview@14.0.1.patch`, applied by pnpm) and a local Expo module, `modules/browser-kit` (Kotlin, Android only), which sets them when the app starts.

- **Plain http:// sites** open (as in every browser) and the address bar marks them "Not secure"; Android blocks cleartext traffic for apps by default, so `plugins/with-web-pages.js` sets `android:usesCleartextTraffic` (it also lets the app reach a sync server on the home network over plain HTTP).
- **WebView settings**: no file or content access, no access from file pages (`allowFileAccess`, `allowFileAccessFromFileURLs`, `allowUniversalAccessFromFileURLs` off), mixed content never loaded, no geolocation, pop-ups only from a tap, third-party cookies off, debugging only in development builds. Google Safe Browsing is on (said explicitly per WebView), and the `X-Requested-With` header that would name Corvus to every site is not sent (`WebSettingsCompat.setRequestedWithHeaderOriginAllowList`, empty). The user agent is the system WebView's without its "wv" mark, which makes some sites (Google sign-in among them) refuse an app's embedded view.
- **No JavaScript bridge**: the app never passes `onMessage`, so no page gets an interface to call. What the app reads from a page (its text for Ask Corvus, the find-in-page count) goes through `evaluateJavascript` and the WebView's own find, whose results only the app sees. The one channel from pages is the cookie banner script's message port, which accepts a few validated reports and runs nothing (see "Cookie banners and Global Privacy Control").
- **Links to other apps** (`intent:`, `market:`, `tel:`, `mailto:`…) never open by themselves: the hook on `shouldOverrideUrlLoading` stops them, and one the person tapped (or a page's redirect right after a tap) is offered in a dialog ("This page wants to open a call to …"). Agreed, `intent:` links are parsed with `Intent.parseUri` and opened only as another app's browsable activity (category `BROWSABLE`, no component or selector a page names, no URI permission grants, never Corvus itself); a link whose app is missing loads its own web fallback (`S.browser_fallback_url`) in the tab. Pages cannot open `file:`, `content:` or top-level `data:` pages. On iOS a tapped link to another app is offered the same way.
- **Camera and microphone**: a page asking for them is refused, and the app says so in a toast. Without the hook the WebView would give a page the camera silently, since Corvus holds the camera permission for scanning the pairing code. Sites cannot use the camera or microphone in 0.7.0.
- **Downloads** go to the system's Download Manager (the Downloads folder, with its notification), with the page's cookies for that site. `blob:` downloads (made by a page's script) are not supported.

### Ad and tracker blocking (Android)

The phone blocks requests to ad and tracker hosts with the filter lists the desktop uses, fetched from the same place (Ghostery's mirror on GitHub of EasyList, EasyPrivacy, Peter Lowe's list and uBlock Origin's filters, privacy and unbreak lists), once a week while blocking is on, as plain files. It is a domain-level blocker, on purpose: a phone has to match every request quickly, and a blocker that never breaks a page beats half of a full engine.

- **What is kept** (`src/lib/blocklist.ts`, tested with `test/blocklist.test.ts`): `||host^` (that host and its subdomains), `||host^$third-party` (only on other sites' pages), `||host/path` prefixes, `@@||host^` exceptions, and per-site element hiding (`site##selector`, plain CSS only). Rules with resource types, `domain=`, redirects or scriptlets, URL patterns without a host, regular expressions and generic element hiding are left out. A page itself (the top frame) is never blocked, nor are local addresses.
- **How**: the lists are compiled in the app (in pieces, so it stays responsive) into a small text file (`corvus-blocklist/compiled.txt`), which the module loads into hash sets; the hook on `shouldInterceptRequest` checks every request of a page against them and answers a blocked one with an empty response. The module counts them per tab and the address bar's shield shows the count. Element hiding is one style sheet added to the page as it loads. The Kotlin matcher (`ContentBlocker.kt`) passes the same cases as the TypeScript one (`modules/browser-kit/android/src/test/resources/blocklist`, run by `ContentBlockerTest` in the Android build).
- **Until the first download** (or if it never can happen), the desktop's built-in fallback list blocks the best-known ad and tracker hosts. Per site, blocking can be turned off from the shield or the menu (the page reloads); Settings lists those sites.
- **Limits**: no blocking on iOS yet (WKWebView would need content rule lists); generic cosmetic filters and scriptlets are not applied, so some sites show empty ad slots or anti-adblock notices; first-party ads served from the site's own host and path patterns without a host are not blocked; video ads on YouTube are not blocked.

### Cookie banners and Global Privacy Control

Since 0.7.0 the phone answers cookie consent banners as the desktop does, with DuckDuckGo Autoconsent (MPL-2.0) and its rules for the common consent platforms and many single sites: it clicks "Reject all", or unticks every purpose and saves; a banner it has rules only to hide is hidden. It also tells every site not to sell or share the person's data with Global Privacy Control. Both are on by default and kept on the phone (Settings → Browser: "Reject cookie banners", Android only, and "Send Global Privacy Control"). The shield's panel says what happened to the page's banner ("Cookie banner rejected (OneTrust)", with `cmpDisplayName` of `@corvus/shared`) and how many were rejected since the app started; "Allow this site's cookie banner" leaves a site's banner to the person (the page reloads; Settings lists those sites, `addSite` / `removeSite`).

- **How (Android)**: `modules/browser-kit` adds two scripts at document start in every frame of every tab (`WebViewCompat.addDocumentStartJavaScript`): `GPC_PAGE_SCRIPT` of `@corvus/shared` (`navigator.globalPrivacyControl` is true) and the banner script, `modules/browser-kit/consent/page.ts` bundled with Autoconsent (88 KB minified). `scripts/consent-assets.mjs` builds both, the packed rules and the license file into the module's assets; the module's Gradle build runs it (task `corvusConsentAssets`), so they always match the installed packages. Turning a switch off removes the script from the tabs' next pages.
- **Untrusted by design**: Android's WebView runs injected scripts in the page's own world (there are no isolated worlds as in the desktop's preloads), so the banner script holds nothing a page could use. Its only link to the app is a `WebViewCompat.addWebMessageListener` object with a name picked at random at each start, which the script hides from enumeration and locks in place before the page's scripts run (it stays on `window`: the WebView finds it there by name to deliver the answer), listening with a listener the page cannot remove. Autoconsent runs as a main-world script (`consentConfig({ mainWorld: true })`), so its snippets for a platform's JavaScript API run in the page and no code ever travels in a message. The module accepts only an init (an `http(s)` address of the frame's own origin, as the WebView reports it) and the events `parseConsentEvent` accepts (`ConsentMessage.kt`; the same cases as the app in `android/src/test/resources/consent/messages.tsv`), at most 200 per page load and 4 KB each; the app checks the events again and only shows them. A page can at worst make its own shield say something false.
- **Each frame gets only its rules**: Autoconsent's compact rules are 368 KB. The script asks for its frame's rules (with its address), and the module picks them natively the way Autoconsent's `filterCompactRules` does (`ConsentRules.kt`, on a packed copy of the rules made by `consent-assets.mjs`; `ConsentRulesTest` checks every pick byte for byte against `filterCompactRules` for some 2,300 pages and frames, built from the rules' own site patterns): a page gets the generic rules (about 133 KB, one string built once) plus those written for its site, a frame only the frame rules (about 5 KB: two generic ones, plus any whose address pattern matches it; Autoconsent's built-in platform code, such as Sourcepoint's frame, runs there too). The rules are read and prepared off the main thread when the feature is turned on; after that a frame is answered at once.
- **Cost** (measured on the emulator, Android 14 x86_64 with WebView 113, while the computer running it was under heavy load, so the spread is wide): evaluating the banner script, which every frame does at document start, takes about 25 ms (7 ms at best); a page's rules answer is parsed and Autoconsent set up in about 60 to 100 ms (12 ms at best); Autoconsent's start at DOMContentLoaded takes under 1 ms (its search for a banner then runs in short asynchronous steps); the answer to the script's request comes back in about 40 ms with the app idle, and in 0.25 to 1 s while the app's main thread is busy drawing (the listener runs on it). Whole page loads with the feature on and off varied more from one run to the next than between the two, so their difference could not be measured there. The GPC script is a few lines. A banner can show for a moment before it is hidden or answered, since the rules arrive after the page has started.
- **The Sec-GPC header**: Android's WebView lets an app add request headers only to the loads it starts (`loadUrl` with headers), so `Sec-GPC: 1` goes with the pages Corvus opens itself (typed in the address bar, links from other apps and from Corvus's own screens), not with links followed inside a page or the requests a page makes (and a reload sends what the load it repeats sent). `navigator.globalPrivacyControl` is set in every frame either way, and that is what consent platforms read. The desktop sends the header on every request.
- **iOS**: Global Privacy Control only: WKWebView adds `GPC_PAGE_SCRIPT` at document start in every frame (react-native-webview's `injectedJavaScriptBeforeContentLoaded`, not limited to the main frame), and the header goes with the pages Corvus opens. Cookie banners are not answered on iOS yet: that needs a native module for WKWebView's content worlds and script message handlers, which the app does not have.
- **Limits**: banners Autoconsent has no rules for stay; the generic rules still run in every page (as in every Autoconsent browser); the WebView must support document-start scripts and message listeners (any current Android System WebView; an older one loads pages without either).

## Default browser (Android)

Corvus for mobile can be the phone's default browser: every link opened on the phone opens in a new tab of Corvus's own browser (since 0.7.0). A person who prefers another browser app picks it under Settings → Open pages in, and links then come to Corvus first, which offers them in one tap to that browser, or sends them to a computer or keeps them (as before 0.7.0).

- **Browser candidate**: `app.json` adds an `android.intentFilters` entry to the main activity (`VIEW` on `http` and `https`, categories `BROWSABLE` and `DEFAULT`, no host), so Android lists Corvus under Default apps → Browser app and in "Open with". iOS gets nothing: Apple lets only real browsers be the default one.
- **Native side**: the local Expo module `apps/mobile/modules/default-browser` (Kotlin, Android only; `expo prebuild` autolinks it from `modules/`, also in the Docker Android build). It tells whether Corvus holds the browser role (`RoleManager.isRoleHeld(ROLE_BROWSER)` on Android 10 and later, the default resolver of a web link before), shows the system's "Set as default browser" dialog (`RoleManager.createRequestRoleIntent`, answered through `startActivityForResult`), falls back to the Default apps settings screen where there is no such dialog, lists the other browser apps (a `<queries>` entry for web links makes them visible on Android 11 and later) and opens a page in one of them by its package. On iOS and in the web build the module is absent and the JavaScript side (`modules/default-browser/index.ts`) is `null`.
- **Links that come in**: expo-router's `redirectSystemPath` (`src/app/+native-intent.ts`, logic in `src/lib/links.ts`) turns an incoming `http(s)` address into `/browser?open=…&incoming=1` (a new tab, which back closes, returning to the app the link came from), or into `/open?url=…` when pages open in another browser app, at a cold start and while the app runs; the app's own `corvus://` links and shares from other apps (`/send`) are untouched. The Open screen (`src/app/open.tsx`, also the browser menu's "Open in…") shows the address with a big **Open in <browser>** button first, then the same send and keep actions as Save or send a page (`src/components/page-actions.tsx`). Unpaired, it offers only Open, with a hint to pair. After Open, or after a page is sent or kept (with a short toast), Corvus steps back (`moveTaskToBack`), so going back from the browser returns to the app the link came from.
- **No loops**: every page the app opens goes through `src/lib/open-url.ts`: to Corvus's browser, or, with another browser app picked, as follows. While Corvus is the default browser on Android, pages for another browser go to the picked browser by its package (`Intent.setPackage`, and `browserPackage` for Custom Tabs), never back to the system, which would hand them to Corvus again. A link Corvus was asked to open always goes there by package, since the person may have picked Corvus "just once". On iOS, on the web and while Corvus is not the default, pages open as before.
- **Which browser**: Settings → Default browser (Android only) says whether Corvus is the default, has "Set as default browser" (the system dialog) and "Open pages in": Corvus (the default) and the installed browsers. The browser that "Open in…" and a long press use is the one picked there; until the person picks one, it is the browser that was the default before Corvus (remembered while it was), else the current default, else the first one found; the choice is kept in AsyncStorage (`src/lib/browser-choice.ts`, tested in `test/browser-choice.test.ts`).
- **The offer**: once paired, Home shows one discreet card, "Make Corvus your default browser", while Corvus is not the default; its close button ("Not now") hides it for good.
- **Try it on a phone**: `adb shell am start -a android.intent.action.VIEW -d https://example.com -n com.parendum.corvus.mobile/.MainActivity` opens the link in a new tab of Corvus's browser (or the Open screen, with another browser app picked) without changing the default browser; `adb shell cmd role get-role-holders android.app.role.BROWSER` shows which app holds the role.

## Develop and check

Everything runs in Docker, from the repository root:

```sh
docker compose run --rm dev pnpm install
docker compose run --rm dev sh -c "pnpm -r build && cd apps/mobile && pnpm typecheck && pnpm test"
docker compose up -d --build sync-server
docker compose run --rm dev sh -c "cd apps/mobile && pnpm export:web && pnpm smoke:web"
```

`pnpm test` covers the pure logic in `src/lib`. `pnpm smoke:web` loads the web build in a headless browser against the real sync server: it pairs, then checks every screen with a fake computer made with `@corvus/sync-core`. Screenshots land in `out/mobile-smoke`.

Icons are drawn from SVG sources in `assets/source` (the Corvus mark of the desktop app): `docker compose run --rm dev bash apps/mobile/scripts/make-icons.sh`. The tab bar's icons are PNGs of the same stroke icons the screens use: `docker compose run --rm dev node apps/mobile/scripts/make-tab-icons.mjs`.

The look comes from one design system: color roles for light and dark, spacing, radii, type scale and elevation in `src/constants/theme.ts`, and the components every screen is built from in `src/components` (buttons, cards and section headers, list rows, text and search fields, chips and segmented controls, the tab strip, empty and loading states, banner, toast and confirmation dialog, the screen scaffold). The icons in `src/components/icon.tsx` are the desktop app's stroke icons, drawn with `react-native-svg`.

## Android builds

`docker compose --profile android run --rm android` generates the native project (`expo prebuild`, never committed) and builds the release APK into `out/mobile/`. With the release key mounted from `../secrets` (`corvus-mobile.keystore` and `corvus-mobile-keystore.env`, kept outside every repository and backed up off the machine) it is signed for release; without it, with the debug key (local testing only). Releases: see "Corvus for mobile releases" in `RELEASE.md`.

With the release key the same run also builds the App Bundle for Google Play, `out/mobile/corvus-mobile-<version>.aab`, signed by Gradle with that key (the generated project would otherwise sign release builds with the debug key).

Release builds are not shrunk with R8 (`-Pandroid.enableMinifyInReleaseBuilds=false`): the Expo template turns it on, and it broke WorkManager, which `expo-background-task` uses, so 0.3.0 and 0.4.0 closed at start-up. Before shipping a build, install it on a phone (`adb install -r out/mobile/corvus-mobile-<version>.apk`) and open it.

**The QR scanner has no Google code.** On Android the pairing code is read by Corvus's own scanner, the local Expo module `modules/qr-scanner`: a CameraX preview whose frames (1280x960, luminance only) are decoded on the phone by ZXing (`com.google.zxing:core`, Apache-2.0, plain Java with no network code), reporting each code to the pairing screen. expo-camera is left out of the Android build (`expo.autolinking.android.exclude` in `apps/mobile/package.json`), because on Android its scanner is Google ML Kit, which sends Google diagnostics, and it also links ML Kit's document scanner and asks Play services to download ML Kit's barcode module. `barcodeScannerEnabled: false` in `app.json` would keep ML Kit out even if expo-camera were linked again. On iOS the app keeps expo-camera, which reads QR codes with Apple's AVFoundation (that option only drops its ZXingObjC reader for other barcode types). `build-android.sh` runs the decoder's tests first (`QrDecoderTest`: real QR images of pairing codes in `modules/qr-scanner/android/src/test/resources/qr`, made by `modules/qr-scanner/scripts/make-fixtures.mjs`: clean, blurred, rotated, tilted, low-contrast, inverted, small) and fails if ML Kit shows up in the APK: its classes (`com.google.mlkit`, ML Kit's internal Play services classes, `androidx.camera.mlkit` from `camera-mlkit-vision`) or anything of it in the manifest. ZXing reads the code with the phone up to about 25 degrees off square (the far edge of the code at least 85% as long as the near one), so the person may need to hold the phone a little straighter than with ML Kit.

## Google Play

The package `com.parendum.corvus.mobile` is registered to Parendum OÜ under Android developer verification (Play Console → Manage account → Android developer verification), with the release key's certificate (SHA-256 `62:68:03:EE:…:30:3C:47:E9`). That covers installing the APK from GitHub on certified phones. Phones with Android Advanced Protection install apps only from Google Play, and Play Protect stays quiet about apps it distributes, so the app also goes to Play:

1. **Create the app** in Play Console (Create app, "Corvus", app, free). The package name is set by the first bundle uploaded.
2. **Play App Signing with our key**, so the Play app and the GitHub APK carry the same signature and update each other: in Test and release → App integrity, choose to use your own key, "Export and upload a key from Java keystore", download Google's `pepk.jar` and encryption public key, then export the release key with them (in the `android` container, where Java is): `java -jar pepk.jar --keystore=/secrets/corvus-mobile.keystore --alias=<KEY_ALIAS> --output=/secrets/play-signing-key.zip --include-cert --rsa-aes-encryption --encryption-key-path=<encryption_public_key.pem>` and upload the zip. The same key stays the upload key, so no second key is needed.
3. **Internal testing**: Test and release → Testing → Internal testing → create a release with the `.aab`, add the testers' Google accounts, and open the opt-in link on the phone. Internal testing is not public and needs no full store listing or review.
4. A public listing (store page, privacy policy, data safety, content rating, review) comes only when Corvus for mobile leaves preview.

Steps 1 and 2 are done (the app exists in Parendum's Play Console with Play App Signing on our key). Every mobile release now goes to internal testing on its own: `apps/mobile/scripts/play-upload.mjs` uploads the bundle through the Google Play Developer API (see "Corvus for mobile releases" in `RELEASE.md`).

Each bundle needs a higher `android.versionCode` in `app.json` than the last one uploaded.

What leaves the phone, for the privacy policy (https://corvus.parendum.com/privacy) and Play's Data safety form:
- The synced records go to the person's sync server end-to-end encrypted; the server also sees device names and types, timestamps and IP addresses. Site icons load straight from each site.
- **QR scanning sends nothing anywhere**: the camera frames and the code are decoded on the phone by Corvus's own scanner (ZXing on Android, Apple's AVFoundation on iOS). Google ML Kit is no longer in the app (earlier versions had it through `expo-camera`, and it sent Google diagnostics).
- `expo-notifications` bundles Firebase Cloud Messaging, but no Firebase project is configured and no push token is requested; `app.json` blocks its `c2dm` permission and Play's install referrer.
- `android.allowBackup` is off: nothing the app stores goes into Android's cloud backup.
- **Browsing** (0.7.0): pages load straight from their sites, like in any browser; there is no Corvus server in between and no telemetry. Searches typed in the address bar go to the search engine picked (DuckDuckGo by default); suggestions while typing come from the phone only. History, open tabs, bookmarks and the reading list sync end-to-end encrypted like the rest. Cookies and site data stay on the phone (Settings → Browser clears them).
- **Google Safe Browsing** is on in the WebView (Android): it checks each address against a list kept on the phone, and only for an address that matches part of it sends a short hash prefix (never the address) to Google to confirm. This is how Chrome and other WebView browsers warn about phishing and malware pages.
- **Filter lists**: while ad and tracker blocking is on, the phone downloads the lists once a week from `raw.githubusercontent.com` (Ghostery's mirror of EasyList, EasyPrivacy, Peter Lowe's list and uBlock Origin's lists, the place the desktop downloads them from), as plain files; nothing about the pages opened is sent. Blocked requests never leave the phone.
- **Cookie banners** (Android): answered on the phone with DuckDuckGo Autoconsent's rules, which ship inside the app (no download, no DuckDuckGo server, nothing about the pages sent anywhere). Corvus clicks the banner's own reject or settings buttons, so the only thing that reaches the site is the person's refusal, as if they had clicked it; the sites the person lets keep their banner and the count of banners rejected stay on the phone.
- **Global Privacy Control**: every page and frame sees `navigator.globalPrivacyControl` (Android and iOS), and the pages Corvus opens itself get the `Sec-GPC: 1` header; it is a signal to sites, nothing is sent to Parendum.
- **Ask Corvus about this page** sends the page's address, title and the start of its text to the person's own computer, through the sync chain (end-to-end encrypted), where Corvus answers with its own AI provider.
- **Sites get no camera, microphone or location** from the browser in 0.7.0 (refused), and no interface into the app.
- **Being the default browser sends nothing anywhere** (Android): the list of installed browsers is read on the phone only (package visibility limited to apps that open `http`/`https` links, no `QUERY_ALL_PACKAGES`), the picked browser is remembered on the phone, and each link goes straight to that browser unless the person sends or saves it, which goes through sync like any other record.

## iOS builds (TestFlight)

Since 0.6.0 the iOS app is built on the Mac build host (the one that builds the macOS desktop release, reached over SSH) and uploaded to App Store Connect, where it becomes a **TestFlight** build of the app "Corvus by Parendum" (bundle `com.parendum.corvus.mobile`, team Parendum OU `PZ5NDD82FC`). It is not on the App Store yet. The release script does it with `-MobileVersion` (`-NoIos` leaves it out); by hand, from the folder that holds the release scripts: `bash ios-release.sh <version> <commit> <repo>` (`--no-upload` builds and signs without uploading).

- **What runs on the Mac** (`ios-build-remote.sh` on a `git archive` of the commit): `pnpm install` of `@corvus/mobile` and its workspace packages, `expo prebuild --platform ios --clean` (the native project is never committed), `pod install` (CocoaPods as a user gem of the system Ruby), manual signing for the app target only, `xcodebuild archive` and `-exportArchive` (method `app-store-connect`), then `altool --upload-app` with the App Store Connect API key. It waits until App Store Connect has processed the build (`VALID`) and makes sure the internal TestFlight group "Parendum" exists with access to every build and every App Store Connect user in it. It stops before building when App Store Connect already has that version and build number.
- **Signing**: an Apple Distribution certificate (Parendum OU, until 2027-10) and an App Store provisioning profile "Corvus App Store", which the build fetches through the API and makes again when it has expired or no longer matches the certificate. The `.p12`, its password and the profile live on the Mac only in `~/corvus-secrets/ios` (and in `../secrets/ios` here, never in a repository). As for the macOS desktop build, tools cannot unlock a keychain they create over SSH on macOS 27, so the build imports the `.p12` into a keychain of its own with a throwaway password and deletes it at the end.
- **Build number**: `ios.buildNumber` in `app.json` follows `android.versionCode` (the release script refuses them different). App Store Connect takes each build number once per version: a second upload of the same version needs both raised.
- **`app.json` for iOS**: `ITSAppUsesNonExemptEncryption: false` (the app uses only standard encryption, so App Store Connect asks no export compliance question per build), `NSLocalNetworkUsageDescription` and `NSAllowsLocalNetworking` (pairing and sync with a server on the computer or the home network over plain HTTP; arbitrary loads stay off), `supportsTablet: false`. expo-notifications gives the app the `aps-environment` entitlement, so the App ID has Push Notifications on, though the app only shows local notifications.
- **Android-only modules**: `modules/qr-scanner` and `modules/default-browser` declare only the `android` platform in `expo-module.config.json`, so autolinking leaves them out of the iOS project; their JavaScript side is `null` there. iOS scans the pairing code with expo-camera (Apple's AVFoundation) and has no default-browser settings.
- **Testers**: members of the App Store Connect team get the TestFlight invitation by e-mail; they install the TestFlight app on the iPhone, accept it and install Corvus from there. A build stays testable for 90 days.

Still missing for the App Store: a share extension (sharing a page to Corvus from other apps; the Android share target exists), the store listing and privacy answers (no tracking, data end-to-end encrypted on the person's own sync server), and review. Background tasks on iOS run when the system decides (often less often than every 15 minutes); the notification text in Settings already says so.
